# Sign tokens with RS256

By default tokens are signed with HS256, and one secret both signs and
verifies them: `SIGNING_KEY`, or `SECRET_KEY` when that is unset. Any server
that can verify a token can also mint one. RS256 splits the two jobs. A
private key signs and a public key verifies, so a service that only checks
tokens can hold the public key and nothing that mints them.

## Install the `rsa` extra

RSA signing needs the `cryptography` package, which the `rsa` extra
installs:

```console
$ pip install "django-signet[rsa]"
```

## Generate a key pair

Generate the keys outside your repository, for example with OpenSSL:

```console
$ openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out signet-private.pem
$ openssl pkey -in signet-private.pem -pubout -out signet-public.pem
```

Both files are PEM text. `signet-private.pem` is the signing key: treat it
like a password, and never commit it. `signet-public.pem` is the verifying
key, and is safe to share.

Put the PEM text in the environment, or have your secrets manager provide it,
and read it from there as this does. A missing variable stops the process at
startup with a `KeyError`, rather than at the first login.

Two system checks guard these keys. See
[`ALGORITHM`](../reference/settings.md#algorithm),
[`SIGNING_KEY`](../reference/settings.md#signing_key) and
[`VERIFYING_KEY`](../reference/settings.md#verifying_key) for the settings.

- **No `VERIFYING_KEY` is error
  [`signet.E004`](../reference/checks.md#signete004---rsa-algorithm-with-no-verifying-key).**
  No token can be signed or verified without it, so login fails with a
  server error, and so does every request that presents a token.
  `manage.py check` fails.
- **No `SIGNING_KEY` is warning
  [`signet.W011`](../reference/checks.md#signetw011---rsa-algorithm-with-no-signing-key).**
  Tokens still verify, but login and refresh fail with a server error,
  because nothing can sign.

the public key:

```{literalinclude} ../examples/rs256_resource_settings.py
:language: python
:start-at: import os
```

On this server `signet.W011` is expected: it cannot sign, and should not.
Silencing it keeps `manage.py check` clean, and `signet.E004` still fails
the check if the public key goes missing.

Its clients send the access token in the `Authorization: Bearer` header,
which they get from a header realm on the issuing server; see
{doc}`header-clients`. Authenticate the resource server's views with
`HeaderJWTAuthentication`.

The resource server still looks the user up. The authentication classes
resolve the token's `sub` to a user in the server's own database, and refuse
an inactive one, so it needs the same user table as the issuing server. A
`Strict*` class also needs the same token store, to check that the session
is live. If you set [`AUDIENCE`](../reference/settings.md#audience) or
[`ISSUER`](../reference/settings.md#issuer), set the same values on both
servers: a token whose `aud` does not match the verifier's is refused.

Do not mount the auth endpoints on a resource server. If it shares the
issuing server's token store, a refresh sent there consumes the refresh
token, then fails to sign its successor and answers 500. The client's retry
at the issuing server presents a spent token, which is reuse, and the
session is revoked.

## Keep the private key out of the repository

- **Only the issuing server gets `SIGNING_KEY`.** Resource servers, CI and
  developers' machines do not need it.
- **Keep it in the environment or a secrets manager**, never in settings
  files, fixtures or the repository. The same goes for local development:
  generate a throwaway pair there.
- **There is one key of each kind.** `VERIFYING_KEY` holds a single public
  key, so replacing the pair invalidates every token signed with the old
  private key, refresh tokens included. Every user logs in again.
- **Changing `ALGORITHM` does the same.** Verification accepts only the
  configured algorithm, so tokens signed with HS256 stop verifying once you
  switch to RS256.
